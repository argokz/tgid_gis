# Шаг 2. Целевая модель «одна таблица — один объект»

## 2.1 Что мешает просто «разложить по таблицам»

Сеть — это граф. Сейчас топология держится на `linesobj.nodeid1/nodeid2 → nodes.id`,
и единое пространство идентификаторов существует ровно потому, что все точки лежат в одной таблице.
Если разложить узлы по 20 таблицам «как есть», ссылаться из линии станет не на что:
внешний ключ не умеет указывать «на любую из 20 таблиц».

Поэтому одной декомпозиции мало — нужен механизм, сохраняющий ссылочную целостность.

Рассмотренные варианты:

| Вариант | Почему не подходит |
|---|---|
| Наследование таблиц (`INHERITS`) | FK на родителя **не видит строки потомков** — целостности не будет |
| Декларативное партиционирование | у партиций обязан быть одинаковый набор колонок, а у `heatsources` их 210, у `connectnodes` — 3 |
| Полиморфная ссылка `(table_name, id)` | FK невозможен в принципе |
| Всё в `jsonb` | QGIS плохо редактирует jsonb, теряется типизация и проверки |

## 2.2 Принятое решение: объектные таблицы + реестр идентификаторов

**Объект живёт в своей таблице и там же хранит свою геометрию.** Целостность обеспечивает
тонкая таблица-реестр, которую наполняют триггеры.

```
net.obj_id_seq                     -- ОДНА последовательность на все объекты:
                                   -- id уникален глобально, в какой бы таблице объект ни лежал

net.node_reg(id PK, kind, tbl)     -- реестр точечных объектов
net.line_reg(id PK, kind, tbl)     -- реестр линейных объектов
```

Каждая объектная таблица:

```sql
CREATE TABLE net.heat_source (
    id          bigint PRIMARY KEY DEFAULT nextval('net.obj_id_seq'),
    fragment_id int  NOT NULL REFERENCES net.fragment(id),
    geom        geometry(Point, 9998) NOT NULL,
    removed_at  timestamptz,
    ...                                  -- 210 своих атрибутов
);
```

и получает триггер, который на `INSERT`/`DELETE` синхронизирует `net.node_reg`.

Линейные объекты ссылаются на реестр — это **настоящий внешний ключ**:

```sql
CREATE TABLE net.pipe_section (
    id        bigint PRIMARY KEY DEFAULT nextval('net.obj_id_seq'),
    node_from bigint NOT NULL REFERENCES net.node_reg(id) ON DELETE RESTRICT,
    node_to   bigint NOT NULL REFERENCES net.node_reg(id) ON DELETE RESTRICT,
    geom      geometry(LineString, 9998) NOT NULL,
    ...
);
```

Что это даёт:

- **QGIS открывает `net.heat_source` напрямую** — обычная таблица, своя геометрия, свой GiST-индекс, редактируемая.
- Удалить узел, на котором висит труба, СУБД не даст (`RESTRICT`) — сейчас это ничем не защищено,
  и в базе уже 1 981 сирота в `heatpipesections`.
- `id` глобально уникален, ссылки между слоями не ломаются.

Цена — по одному триггеру на объектную таблицу, срабатывает только на вставке и удалении.

## 2.3 Геометрия становится единственным источником координат

Сейчас координаты живут в трёх местах и расходятся. В целевой модели остаётся только `geom`.

Восстановленное правило преобразования (проверено на **49 079 из 49 079** записей, совпадение 100 %):

```
внутренние единицы ТГИД = сантиметры, ось Y направлена вниз

geom_узла  = ST_SetSRID(ST_Point(x / 100.0, -y / 100.0), 9998)
geom_линии = ST_MakeLine( geom(node_from), parse(coords)…, geom(node_to) )
```

`linesobj.coords` содержит **только промежуточные** вершины; концы всегда берутся из узлов.
Разделитель — пробел или запятая вперемешку, парсер — [`coordlis.cpp:1140`](../../gid8/gid8/cxema/coordlis.cpp).

Побочный, но крупный эффект: конвертер **достраивает недостающую геометрию**.

| | живых (`removed=0`) | `shape` есть сейчас | можно построить | прирост |
|---|---|---|---|---|
| узлы | 86 624 | 53 966 | **86 582** | +32 616 |
| линии | 121 058 | 45 917 | **80 614** | +34 697 |

### Открытие: треть «линий» — это вообще не линии

Из 121 058 живых записей `linesobj` только **80 636 имеют заполненные концы**.
У оставшихся **40 422 записей `nodeid1` и `nodeid2` равны NULL** — вместе с `fileid`
и `internalnodeid`. Заполнены только `externalsignlineid`, `location`, `typ`, `organizationid`.

Геометрии у них нет и быть не может: `shape` пуст у всех 40 422, `coords` заполнен у 30.

Что это на самом деле — видно по разбивке:

| Подтип | Записей без концов |
|---|---|
| `diaphragms` | 14 140 |
| `dampers` | 11 813 |
| `heatpipesections` | 11 382 |
| `elevators` | 2 206 |
| `systemradiators` | 516 |
| `heatexchangers` | 228 |

Это **оборудование внутренних схем тепловых пунктов** — элеваторы, шайбы, задвижки,
теплообменники внутри ИТП/ЦТП. В ТГИД они регистрируются как записи `linesobj`
ради единого пространства идентификаторов, но топологии и координат у них нет
по построению: внутренняя схема потребителя рисуется по шаблону из справочника `b5`
(«структура оборудования схемы»), а не по координатам на карте.

Практический вывод: это **не повреждённые данные и не сироты**, а полноценная
пятая категория объектов — непространственная.

| Категория | Куда переносится |
|---|---|
| `equipment` | таблицы `net.equipment_*` **без геометрии**, привязка к родительскому потребителю |

В ГИС-слои они не попадают и попадать не должны — иначе 40 тысяч объектов без координат
засорят карту.

### Вопрос закрыт: решения заказчика не требуется

Первоначально предполагалось, что это действующие внутренние схемы тепловых пунктов
и что нужна отдельная категория `equipment`. **Предположение оказалось неверным.**

Настоящие внутренние схемы создаются `create_b5` как обычные узлы и линии
с заполненными концами — в базе их 1 498 узлов и 1 085 линий, и они перенесены
в `net` штатно. А записи с пустыми концами не читает **ни один** путь кода:
везде внутреннее соединение `JOIN nodes ON n.id = l.nodeID1`.

Разбор с доказательствами — [05-orphan-equipment.md](05-orphan-equipment.md).

Решение конвертера складывать их в `net.line_orphan` корректно: операционно
не теряется ничего, данные сохранены целиком. Категория `equipment` не нужна.

## 2.4 Прочие решения по схеме

| Сейчас | Станет | Зачем |
|---|---|---|
| `removed int` + `idremoved` | `removed_at timestamptz` + частичные индексы `WHERE removed_at IS NULL` | рабочие индексы вдвое меньше, «живые» выборки не читают удалённое |
| нет индексов по `nodeid`/`lineid` | индекс на каждую ссылку | все джойны идут именно по ним |
| 226 пустых таблиц | не переносим | 35 % схемы — мусор |
| дубли `obekty`/`tablitsa1`, `zhile`/`zhile1`, `vvod_v_zdanie`/`vvody_v_zdanie` | одна таблица, вторая — в отчёт о расхождениях | |
| `audit_log` 112 MB без ретенции | партиционирование по месяцам + политика хранения | 20 % размера БД |
| SRID 9998 без трансформации | `geom` в 9998 + вычисляемый `geom_4326` для веб-ГИС | QGIS/GeoServer/OSM |

## 2.5 Стратегия миграции — как не сломать работающее

Ключевое наблюдение: **запросы чтения схемы лежат в файлах `sql3/us.sql` и `sql3/ut.sql`,
а не в коде C++**. Значит основную часть перевода можно сделать, не перекомпилируя приложение.

| Фаза | Действие | Риск | Откат |
|---|---|---|---|
| 0 | Создать схему `net` рядом. `public` не трогаем | нет | `DROP SCHEMA net` |
| 1 | Конвертер наполняет `net`. Идемпотентный, с отчётом валидации | нет | повторный прогон |
| 2 | Слой совместимости: `public.nodes` → `public.nodes_legacy`, вместо неё обновляемое представление над `net.*` | средний | переименовать обратно |
| 3 | Переписать `us.sql`/`ut.sql` на `net` напрямую | низкий | вернуть старые файлы |
| 4 | Правки в C++/Python: запись, новые слои, параметризованные запросы | средний | по коммитам |

Фазы 0–1 полностью безопасны: рабочая база продолжает жить в `public`, `net` наполняется параллельно.
Приложение переключается только на фазе 2, и переключение обратимо переименованием.

## 2.6 Ожидаемый выигрыш в скорости

Сейчас на каждое открытие схемы выполняется джойн 26 таблиц, возвращающий 160+ колонок
на 121 058 линий (2 059 мс) и 91 узел плана на 86 624 узла (1 124 мс) — **на пустых таблицах результатов**.

В целевой модели:

1. Отрисовке карты нужно ~15 колонок, а не 160 — отдельное «тонкое» представление для рендера.
2. Нет джойнов подтипов: тип объекта = имя таблицы.
3. Результаты расчёта подтягиваются отдельным запросом только когда их показывают,
   а не при каждом чтении схемы.
4. Частичные индексы `WHERE removed_at IS NULL` + GiST по `geom` + фильтр по `fragment_id`.

Замеры «до/после» на тех же данных — обязательная часть шага 5, цифры пойдут в отчёт.

## 2.7 Уточнение: не всякий «подтип» является классом объекта

Первоначальное допущение «каждая таблица-подтип = отдельный класс объекта» **проверку не прошло**.
Измерения ([`tools/check_cardinality.py`](../tools/check_cardinality.py),
[`tools/check_overlap.py`](../tools/check_overlap.py)) показали:

**Узел может состоять сразу в нескольких подтипах** — 4 126 узлов из 61 381, один узел в 11 таблицах:

| Сочетание | Узлов |
|---|---|
| `consumer_general` + `press_set_node` | 2 482 |
| `consumer_general` + `direction_deployed` | 804 |
| `connect_node` + `regulator_press` | 229 |
| `heat_source` + `press_set_node` | 136 |
| `consumer_general` + `consumer_general` (две строки на один узел) | 119 |

**Часть «подтипов» вообще не связана с `nodes`** — ссылка пуста во всех строках,
а собственная геометрия заполнена на 100 %:

| Таблица | Строк | `nodeid` заполнен | `shape` заполнен |
|---|---|---|---|
| `ugol_povorota_truboprovoda` | 25 214 | **0** | 25 214 |
| `lyuki` | 18 392 | **0** | 18 392 |
| `vvod_v_zdanie` | 5 463 | **0** | 5 463 |
| `vvody_v_zdanie` | 5 463 | **0** | 5 463 |
| `opora` | 3 611 | **0** | 3 611 |
| `perehod_diametra` | 4 | **0** | 4 |

Это уже самостоятельные ГИС-слои (судя по всему, импортированные извне), а не подтипы узлов.

Итоговая классификация — **четыре категории вместо одной**:

| Категория | Что это | Куда переносится | Таблиц |
|---|---|---|---|
| `class_node` / `class_line` | настоящий класс объекта, связь заполнена, 1:1 | своя таблица с геометрией | 9 + 9 |
| `layer` | самостоятельный слой, геометрия своя, связи нет | своя таблица как есть | 12 |
| `aspect` | 1:1, но узел принадлежит другому классу (`setpressnodes`) | дочерняя таблица | 1 |
| `child` | честная связь 1:N (`wdodevices` — до 10 приборов на узел, `deployeddirections` — до 4) | дочерняя таблица | 2 |
| `junk` | ни геометрии, ни связи (`pressdropregulators` 13, `consumptregulators` 7) | не переносится, идёт в отчёт | 2 |

Если бы аспекты и дочерние таблицы стали «объектами», один физический узел размножился бы
на несколько объектов с одинаковой геометрией — сеть перестала бы быть графом.

### Требуют решения заказчика

- 119 узлов имеют **две строки** в `generalizedconsumers` (и по одному дублю в `realconsumers`,
  `heatsources`, `pumpstations`, `pressregulators`). Какую строку считать верной?
  До решения конвертер берёт строку с наибольшим `id` и пишет вторую в `net.conversion_reject`.
