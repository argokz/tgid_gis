# Шаг 25. Работа над скоростью расчёта

Цель, поставленная заказчиком: ускорить приложение примерно в полтора раза.
Приложение производственное, поэтому порядок работы такой: одна правка —
замер — сверка результатов — коммит или откат.

## 25.1 Сначала пришлось починить измерение

Первые попытки оптимизации оценивались одиночным прогоном. Это оказалось
негодным методом: один и тот же **неизменённый** код давал 16.65, 18.79
и 21.51 секунды. Разброс превышал искомый эффект, и по одиночным цифрам
делались неверные выводы «стало хуже».

[`tools/bench_calc.py`](../tools/bench_calc.py) выполняет несколько прогонов
и показывает минимум, медиану и разброс. Минимум ближе всего ко времени
без посторонней нагрузки.

Текущая база (фрагмент 2, БД `tgid_gis`, 3 прогона):

| | секунд |
|---|---|
| минимум | **20.4** |
| медиана | 20.8 |
| максимум | 22.6 |
| разброс | 2.2 (11 %) |

**Практическое следствие:** правка должна давать больше 11 %, иначе на трёх
прогонах её не отличить от шума. Для мелких правок нужно больше прогонов.

## 25.2 Куда уходит время

[`tools/pyprofile_calc.py`](../tools/pyprofile_calc.py) — профиль на уровне
функций Python. Профилирование примерно удваивает время, поэтому смотреть
надо на доли, а не на абсолютные значения.

| Блок | Доля |
|---|---|
| `w_calc` — решатель | 48 % |
| `w_out` — запись результатов | 28 % |
| `read_gid` — чтение данных | 23 % |

Внутри решателя:

| Что | Время (профиль) | Вызовов |
|---|---|---|
| `networkx.edge_dfs` | 7.9 с | 96 161 шаг обхода |
| `make_matrix` | 5.3 с | 3 327 |
| разреженная матрица: поэлементная запись и конверсии | ~3 с | 100 352 |
| `pyodbc.execute` | 6.3 с | 74 запроса |

Структура задачи: **350 подсетей**, каждая решается отдельно, до 20 итераций
на подсеть.

## 25.3 Две попытки, обе отклонены

**Обновление матрицы на месте.** Матрица LIL переписывается поэлементно
и целиком конвертируется в CSC на каждой из 3327 итераций, хотя структура
не меняется. Сделал построение CSC один раз и запись прямо в массив `data`
по заранее вычисленным позициям.

Замер дал 22.65 с против 16.65 — отклонено. **Но этот вывод сомнителен:**
он получен до наладки измерения, а текущая база 20.4 с. Правку стоит
проверить заново на надёжном стенде.

**Кэш обхода графа.** Предполагалось, что `set_G_num`, `init_root`
и `init_matrix` обходят один и тот же граф по три раза. Кэш дал 18.79 с
и, что важнее, **логически не сработал**: кэш не попадал, потому что
обходы идут по разным объектам подграфов. Отклонено обоснованно.

Попутно вскрылась ошибка: первая версия кэша хранила данные в `G.graph`,
а у подграфов networkx этот словарь **общий с родителем** — обход одной
подсети применялся к другой, расчёт падал с `KeyError`.

## 25.4 Первое принятое ускорение: обновление матрицы на месте

После наладки стенда правка перепроверена и **принята**.

Суть: строение матрицы задаётся при первой сборке и дальше не меняется,
а между итерациями обновляются только диагональные элементы — это видно
по коду, все семь записей вне ветки `if first` имеют вид `matrix0[k_l, k_l]`.
Раньше на каждой из 3327 итераций выполнялась поэлементная запись в LIL
и полная конверсия LIL → CSC.

Теперь CSC строится один раз, позиции диагонали запоминаются массивом,
и обновление — это присваивание в `data` по индексу.

| | минимум | медиана | максимум |
|---|---|---|---|
| было | 20.4 с | 20.8 с | 22.6 с |
| стало | **18.4 с** | **18.9 с** | **20.2 с** |

Выигрыш около 10 %. Он на границе разброса, но все три величины сдвинулись
согласованно — это надёжнее одиночного замера.

Результаты расчёта не изменились: `us_out` макс 0.0202297, `ut_out` макс
0.194513, `pt_out` макс 0.144731 — те же цифры до последнего знака.

## 25.5 Подсети распределены равномерно — параллельность применима

[`tools/graph_shape.py`](../tools/graph_shape.py) измеряет размеры слабо
связных компонент, на которые решатель разбивает схему:

| | значение |
|---|---|
| компонент (более одного узла) | 403 |
| узлов в них | 5 469 |
| крупнейшая компонента | 152 узла, **2.8 %** |
| четыре крупнейших | 8.8 % |

Узкого места нет: работа размазана ровно. Это лучший случай для
параллельного счёта — закон Амдала не мешает.

Попутное наблюдение: средняя компонента — около 14 узлов, а решается 27 мс.
Для системы такого размера линейная алгебра занимает микросекунды, значит
время съедают накладные расходы Python на каждой из 3327 итераций.
Отсюда и сработала правка выше, и отсюда же следует, что параллельность
даст выигрыш — она распараллеливает именно накладные расходы.

## 25.6 Профиль после первой правки

`make_matrix` упал с 5.26 до **1.74 с** — правка подтвердилась и на профиле.
Новое распределение:

| Что | Время (профиль) | Вызовов |
|---|---|---|
| `pyodbc.execute` | 6.33 с | 74 запроса |
| `networkx.edge_dfs` | 7.36 с | 96 161 шаг |
| `read_line2` | 3.61 с | 14 |
| `make_matrix` | 1.74 с | 3 327 |

### Ложный след, который я едва не принял за находку

По замеру через `psql -c` выходило, что запрос к **пустой** таблице
занимает 159–211 мс, и напрашивался вывод: тринадцать пустых классов
съедают около 2.3 секунды впустую.

Замер в одном соединении показал другое:

| таблица | строк | запрос |
|---|---|---|
| `elevator`, `diaphragm`, `air_heater`, `damper` | 0–599 | **2–3 мс** |
| `pipe_section` | 84 624 | 197 мс |

Те 200 мс были запуском процесса `psql`, а не запросом. Пустые таблицы
не тормозят, оптимизировать там нечего.

Вывод для методики: замер внешней утилитой включает её собственный старт.
Для запросов в миллисекундном диапазоне мерить надо внутри одного
соединения.

## 25.7 Парный замер: без него оптимизации нельзя принимать

Материализация подсетей (`G.subgraph(i)` — это ВИД, каждое обращение
к соседям проходит фильтрацию) выглядела очевидным выигрышем: по профилю
на фильтрации уходило 258 тысяч вызовов `edge_ok`.

Первый замер подтвердил: минимум упал с 18.4 до 15.2 секунды. Но повторный
замер того же кода дал 21.6 — машина была загружена иначе. Разброс достигал
23 %, и варианты, измеренные в разное время, оказались несравнимы.

[`tools/ab_calc.py`](../tools/ab_calc.py) чередует варианты A-B-A-B в одном
сеансе, поэтому оба видят одинаковые условия. Результат:

| вариант | мин | медиана | макс |
|---|---|---|---|
| вид (как было) | 15.8 | 18.5 | 19.8 |
| копия | 15.7 | 17.7 | 20.0 |

Попарная разность: −0.5, +0.6, −2.0, +3.4 секунды. **Знак непостоянен**,
медиана разности +0.1 с. Выигрыша нет: копирование 403 графов стоит
примерно столько же, сколько экономит на обходе.

Правка откачена. Без парного замера в производственный код ушло бы
усложнение — копия плюс обратный перенос атрибутов — ради нуля.

**Правило для дальнейшей работы:** оптимизация принимается только после
парного чередующегося замера, где знак разности одинаков во всех парах.

## 25.8 Параллельный счёт: выполнимость подтверждена

[`tools/probe_parallel.py`](../tools/probe_parallel.py) измеряет цену
подготовки данных для рабочих процессов — до того, как писать
параллельный код. С материализацией подсетей вышло именно так: копирование
съело весь выигрыш, и узнали мы это уже после правки.

| | |
|---|---|
| подсетей | 403 |
| создание видов | 0.02 с |
| копирование | 0.40 с |
| сериализация | 0.09 с (3.9 МБ) |
| десериализация | 0.11 с |
| **накладные расходы** | **0.60 с** |
| ядер в системе | **8** |

Накладные расходы малы. Решатель занимает около 8.6 с из 18; на нескольких
ядрах он ужмётся до ~2 с. Чистый выигрыш ожидается 20–25 % с учётом
запуска рабочих процессов.

### Что придётся затронуть

Решатель опирается на состояние уровня модулей, и в рабочем процессе его
нужно воссоздать:

| Что | Где | Как передать |
|---|---|---|
| `config.args` | `sety.config` | повторный разбор тех же аргументов |
| справочники | `sety.sprav` | перечитать из БД или передать словарями |
| расчётные температуры | `sety.ct` | то же |
| `w_print.G_main` | `sety.w_print` | назначить подсеть; влияет только на текст сообщений |

Запуск рабочего процесса на Windows идёт через `spawn`, то есть каждый
заново импортирует модули и поднимает справочники — около 2 с. Это разовая
плата, и пул надо создавать один раз на расчёт, а не на подсеть.

### Честная арифметика по цели

| | вклад |
|---|---|
| матрица на месте (принято) | 10 % |
| параллельный счёт (ожидается) | 20–25 % |
| запись результатов (28 % времени, нулевой риск для чисел) | до 10 % |

Полтора раза одной правкой не получить: нужны все три. Параллельность —
самая крупная и самая рискованная, поэтому её стоит делать отдельной
работой с полным прогоном регрессии, а не в хвосте общей сессии.

## 25.9 Параллельный счёт: реализован, измерен, отклонён

Реализация рабочая и численно верная — результаты совпали с последовательным
путём до последнего знака. Но выигрыша нет.

| вариант | мин | медиана | попарная разность |
|---|---|---|---|
| последовательно | 18.1 | 19.0 | — |
| 4 процесса | 16.1 | 18.1 | +2.1, +0.2, +1.5, −0.5 → знак непостоянен |
| 8 процессов | 19.9 | 22.8 | −5.3, −1.9, −4.0, −4.0 → **хуже во всех парах** |

Четыре процесса дают около 5 % и не отличимы от шума. Восемь — устойчиво
хуже на 22 %: запуск процессов съедает больше, чем даёт распараллеливание.

### Где я ошибся в оценке

Ожидание 20–25 % строилось на доле решателя **из профиля** — 48 %.
Но профилирование удваивает время интерпретируемого кода, а ожидание
ввода-вывода не удваивает. В реальном прогоне доля решателя заметно ниже,
поэтому и параллелить оказалось почти нечего: замер по фазам
(`profile_calc.py`, без cProfile) даёт 10.9 с на «решатель и запись»
из 17 с, и собственно решатель — примерно 7 с.

При запуске четырёх spawn-процессов, каждый из которых заново поднимает
справочники и таблицы b5, накладные расходы съедают почти весь выигрыш.

**Правило:** доли из профиля годятся, чтобы выбрать, куда смотреть,
но не годятся, чтобы предсказывать выигрыш. Для предсказания нужен замер
фаз без профилировщика.

### Что сделано с кодом

Правка из ядра откачена. Рабочая реализация сохранена в репозитории как
[`experiments_parallel_solver.py`](../experiments_parallel_solver.py) —
чтобы не повторять эксперимент заново. В производственном коде
выключенного пути не оставлено: он не помогает, а сопровождать пришлось бы.

## 25.10 Итог по скорости и что делать дальше

Проверено и закрыто:

| Кандидат | Итог |
|---|---|
| обновление матрицы на месте | **принято, ~10 %** |
| кэш обхода графа | отклонён: кэш не попадает |
| материализация подсетей | отклонён: знак разности непостоянен |
| параллельный счёт, 4 процесса | отклонён: +5 %, в пределах шума |
| параллельный счёт, 8 процессов | отклонён: −22 % |
| запись результатов | крупной цели нет: собственное время размазано, максимум 2–3 % |

### Что осталось и чего это стоит

Системная причина видна по профилю: время съедают **накладные расходы
networkx** — `reportviews`, `coreviews`, `edge_dfs`, обращения к словарям.
Они присутствуют одинаково в решателе, в чтении и в записи.

Обойти их точечными правками не выходит — это показали четыре отклонённых
эксперимента. Остаются два пути, оба крупные:

1. **Заменить networkx на массивы.** Граф хранить как массивы `numpy`
   (индексы узлов, рёбер, атрибуты), а не как словари словарей. Это даёт
   кратное ускорение, но переписывает ядро целиком.
2. **Считать несколько фрагментов одновременно** на уровне приложения,
   а не подсети внутри одного расчёта. Пул поднимается один раз,
   startup амортизируется по всему пакету расчётов.

Второй путь дешевле и не трогает численный код. Он полезен, когда
пользователь считает несколько фрагментов подряд — типичный сценарий
эксплуатации.

Ни одна правка не принимается без сверки результатов
[`tools/compare_calc.py`](../tools/compare_calc.py): расчёт чувствителен
к порядку обработки, и быстрый неправильный ответ хуже медленного правильного.

## 26. Потолок замены networkx на массивы: измерен

Прежде чем переписывать ядро, надо знать верхнюю границу выигрыша.
[`tools/probe_arrays.py`](../tools/probe_arrays.py) выполняет одни и те же
действия на **реальном** графе двумя способами: обход networkx с чтением
атрибутов из словарей — и те же данные в массивах `numpy` с доступом по
индексу. Числовая часть и работа с БД в замер не входят: иначе потолок
получился бы завышенным.

Фрагмент 2, 403 подсети, 5 553 узла, 6 478 рёбер:

| Вариант | Один полный проход |
|---|---|
| networkx, словари | 0.337 с |
| массивы, индексы | 0.007 с |
| **отношение** | **48x** |

Подготовка массивов из того же networkx — 0.409 с разово.

### Сколько это в масштабах расчёта

48x — это отношение на обходе, а не выигрыш расчёта. Доля обхода считается
так: профиль дал 96 161 шаг `edge_dfs` при 6 478 рёбрах, то есть **14.8
полных проходов** по всем подсетям. При 0.30–0.34 с за проход обход
занимает **4.4–5.0 с из ~18 с, то есть около 25 %**.

Ускорить 25 % в 48 раз — значит убрать почти все эти 25 %. Но это по-прежнему
**потолок, а не прогноз**: в микрозамере тело цикла состоит из трёх чтений
атрибутов, а в настоящих циклах на каждое ребро приходятся ещё условия,
вызовы функций и арифметика, которые от массивов не ускорятся. Реалистичная
оценка — **10–15 %**, потолок 25 %.

Цена: 374 обращения к networkx в 34 файлах, шесть графовых алгоритмов
переписать заново, эквивалентность результата проверяется только сверкой
чисел. **Цель в 50 % этим путём не достигается.** Решение о переписывании
ядра принимается заказчиком с этими цифрами на руках, а не «под кратное
ускорение».

## 27. Почему материализация подсетей была не просто бесполезна, а опасна

Отклонённый в 25.8 эксперимент стоит перечитать: замер тогда показал
непостоянный знак разности, и на этом всё закончилось. Проверка показала,
что дело хуже.

Отдельный замер обхода:

| Обход 403 подсетей | Время |
|---|---|
| по видам `G.subgraph(i)` | 0.297 с |
| по копиям `.copy()` | 0.110 с |
| вид дороже копии в | **2.7 раза** |

По этой арифметике материализация должна была дать ~2.8 с — а не дала
ничего. Причина в том, что копия **не эквивалентна** виду:

- у вида `GG = G.subgraph(i)` ([`w_calc.py:1158`](../../gid8/python/sety/sety/w_calc.py))
  словари атрибутов **общие** с `G`;
- расчёт пишет результаты в узлы и рёбра `GG`;
- `g2.write_po(G, param_sum, ...)` на строке 1201 читает их **из `G`**.

У копии словари свои. Результаты расчёта остались бы в копии и не дошли
до записи. То есть материализация подсетей — не «оптимизация без выигрыша»,
а **тихая потеря результатов**. Ускорение обхода в 2.7 раза этим путём
недоступно в принципе.

Это же ограничение действует и на замену networkx массивами: массивы
годятся для **чтения** в горячих циклах, но запись результатов обязана
идти в общие с `G` словари.

## 28. Надёжность: два дефекта в записи результатов

Запись `*_OUT` уже пакетная — 1 000 строк одним `INSERT`, крупной цели по
скорости там нет (см. 25.10). Но в
[`any/insert2.py`](../../gid8/python/sety/sety/any/insert2.py) нашлись два
дефекта.

**`cols` был атрибутом класса, а не экземпляра.** Все 11 таблиц —
`PT_OUT`, `UT_OUT`, `US_OUT`, `NS_OUT`, `RS_OUT` и остальные — складывали
имена колонок в один общий набор. Проверка в `db_write` сверяла колонку
с объединением колонок всех таблиц, то есть пропускала колонку чужой
таблицы. Осмысленное сообщение «Нет колонки X в таблице Y» подменялось
отказом SQL на вставке, где связь с причиной уже не видна.

**`db_write0` вызывала `db_write` как свободную функцию.** Такой функции
в модуле нет — любой вызов упал бы с `NameError`. Метод сейчас нигде не
используется, поэтому дефект не проявлялся.

Проверка: полный расчёт фрагмента 2 прошёл за 15.67 с, ни одна колонка на
ужесточённую проверку не наткнулась, сверка с эталоном совпала с
зафиксированной в [09](09-calc-regression-results.md) — `ut_out`, `ns_out`,
`rs_out` без расхождений, `pt_out` те же 5 ячеек с макс 5.16. Правка
численно инертна: `cols` участвует только в проверке, `db_write0` не
вызывается.

## 29. Правки sety теперь под учётом

Движок расчёта живёт вне репозитория — `gid8/python/sety`, 103 файла,
24 679 строк. Копировать его сюда значит завести форк, который начнёт
расходиться с оригиналом. Но и без учёта оставлять нельзя: при
переустановке sety все наши правки молча исчезнут, а обнаружится это
замедлением расчёта или запросами к несуществующим таблицам.

[`tools/sety_patches.py`](../tools/sety_patches.py) хранит реестр из семи
правок (net_mode, развилка чтения, матрица на месте, оба фикса insert2)
и проверяет, что каждая на месте:

```bash
python tools/sety_patches.py
```

Проверка не заменяет регрессию расчёта — она отвечает на другой вопрос:
«наши правки вообще ещё в исходнике?»
