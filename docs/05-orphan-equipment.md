# Шаг 16. Что делать с 40 412 записями оборудования — вопрос закрыт

Ранее это было вынесено как решение, которое должен принять заказчик
([02-target-model.md](02-target-model.md), «Открытый вопрос»).
Вопрос удалось закрыть измерением и разбором кода, решения не требуется.

## Что это за записи

40 412 живых записей `linesobj` имеют `nodeid1` и `nodeid2` равные NULL:
14 140 диафрагм, 11 813 задвижек, 11 382 участка, 2 206 элеваторов,
516 радиаторов, 228 теплообменников. Геометрии у них нет и быть не может.

Первая гипотеза была, что это действующие внутренние схемы тепловых пунктов.
**Гипотеза неверна.**

## Как устроены настоящие внутренние схемы

Внутреннюю схему строит `create_b5` ([gidview/b5.cpp:425](../../gid8/gid8/gidview/b5.cpp))
по шаблону из справочника «структура оборудования схемы». Она вызывает
`addNodeUS(db, "nodes", ...)` с заполненным `internalNodeID` (ссылка на
родительский узел) и затем `addLine(...)` — то есть создаёт **обычные узлы
и обычные линии с заполненными концами**.

В базе это подтверждается:

| | записей |
|---|---|
| узлов внутренних схем (`internalnodeid` заполнен) | 1 498 |
| линий между узлами внутренних схем | 1 085 |
| записей оборудования с пустыми концами | 40 412 |

Действующие внутренние схемы — это те самые 1 498 узлов и 1 085 линий,
и они перенесены в `net` как обычные объекты.

## Их не читает ни один путь кода

Проверены все места, где приложение обращается к оборудованию:

| Путь | Условие соединения | Итог |
|---|---|---|
| `sql3/ut.sql` — чтение схемы | `JOIN nodes n1 ON n1.id = l.nodeID1` | исключает NULL |
| `getLineQ` — [gidr_add.cpp:64](../../gid8/gid8/gidview/gidr_add.cpp), внутренние схемы | `FROM linesobj l1, %1 l2, nodes WHERE l1.nodeID1 = nodes.ID` | исключает NULL |
| отчёты `sql/EL.sql`, `DR.sql`, `ZD.sql` | `join nodes n1 on n1.id = l.nodeID1` | исключает NULL |
| расчётное ядро `sety` (Python) | читает граф из тех же выборок | исключает NULL |

Прямых обращений к `elevators`, `diaphragms`, `dampers`, `heatexchangers`,
`systemradiators` без соединения с `nodes` в коде нет — проверено поиском
по C++ и Python.

Везде **внутреннее** соединение, поэтому строка с `nodeid1 IS NULL`
не попадает в выборку никогда.

## Вывод

Это остатки прежней системы: оборудование, чья привязка была потеряна.
Приложение их не видит уже много лет, расчёт их не использует, в отчёты
они не попадают.

Решение конвертера — складывать их в `net.line_orphan` — **корректно**:
операционно не теряется ничего, а данные сохранены целиком (вместе
с полным содержимым строки в поле `payload`) на случай разбора.

Отдельной таблицы `net.equipment_*` создавать не нужно: переносить в рабочую
модель нечего.

## Что с этим делать дальше

Это данные для чистки, а не для миграции. Разумный порядок:

1. выгрузить из `net.line_orphan` в отчёт с разбивкой по типу и году;
2. согласовать с эксплуатацией, что записи действительно не нужны;
3. удалить из `public.linesobj` вместе со строками подтипов —
   это освободит около трети записей таблицы и ускорит все выборки по ней.

До согласования ничего не удаляем.
