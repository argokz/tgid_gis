# Перевод gid8 на новую БД

## Замер: сколько там работы

[`tools/gid8_tables.py`](../tools/gid8_tables.py) собирает имена таблиц
из всех `.cpp`, `.h`, `.sql` приложения и сверяет с живой БД.

| | |
|---|---:|
| файлов с обращениями к БД | 403 |
| различных имён таблиц | 472 |
| `nodes` встречается в | **219 файлах** |
| `linesobj` | 112 |
| `fragments` | 109 |
| `heatsources` | 82 |
| `realconsumers` | 80 |
| `generalizedconsumers` | 68 |

Переписать это на `net` — значит переписать приложение. Месяцы работы
и риск сломать то, что работает.

## Решение: слой совместимости в отдельной схеме

Представления старой модели возвращены, но **не в `public`**, а в схему
`compat` ([`sql/171_compat_for_gid8.sql`](../sql/171_compat_for_gid8.sql),
20 представлений над `net.v_*`).

`compat` **не входит в `search_path` базы**:

```
search_path базы: public, net, ref, calc, addr, doc, el, ops, org
```

Значит Qt-клиент, движок расчёта и QGIS её не видят и работают с
продуктовой моделью напрямую. Видит её только gid8, который задаёт свой
порядок поиска при подключении — одна строка в
[`gid8/gid8/db/db.cpp`](../../gid8/gid8/db/db.cpp), рядом с уже
существующим `set application_name`:

```cpp
query.exec("set search_path = compat, public, net, ref, calc,"
           " addr, doc, el, ops, org;");
```

Так выполняются оба требования сразу: gid8 работает полностью, а
«ничего старого» остаётся верным для всех, кто работает с продуктовой
моделью. Когда gid8 выведут из эксплуатации,
`DROP SCHEMA compat CASCADE` — и больше ничего не задето.

**Приложение нужно пересобрать**: правка в `db.cpp` — единственное
изменение в C++.

## `fragments`: три таблицы обратно в одну

Фрагмент разложен на `net.fragment` (паспорт, 22 поля),
`net.fragment_system` (12 параметров × 5 систем) и `net.fragment_month`
(6 параметров × 12 месяцев) — обоснование в
[15](15-fragment-and-subsystems.md). gid8 обращается к плоской
`fragments` из 109 файлов, поэтому
[`sql/172_compat_fragments.sql`](../sql/172_compat_fragments.sql)
собирает все 156 колонок обратно: 12 соединений по месяцам и 5 по
системам.

Представление только для чтения: разобрать плоскую строку обратно в
дочерние таблицы однозначно нельзя, а править параметры фрагмента из
gid8 не требуется.

Сверка — [`sql/tests/test_compat_fragments.sql`](../sql/tests/test_compat_fragments.sql):
**все 154 колонки** совпадают с исходной таблицей. Не выборка: ошибка в
одном из 132 соединений по индексу выглядит как успех, если смотреть на
пару значений.

## Что осталось

Ещё 343 имени не разрешаются, но почти все — не про C++:

* **`the`, `a`, `spatial_ref_sy`** — ложные срабатывания разбора: слова
  из текста и обрезанные имена.
* **`tempview`, `tempviewfact`** — временные представления, которые
  создаются на ходу.
* **`realconsumers2`, `heatlosessourcefact`, `tankbatteries`,
  `responsibles`, `heatpipesectionsharness`** — подсистема отчётов
  `python/poteriNewPg`, отдельное приложение со своими запросами.
* **`consumptregulators`, `bypass` и ещё три** — на чердаке; в gid8
  встречаются только в скриптах конвертации `new_baza/conv/`, которые
  при работе не выполняются.

То есть для самого gid8 закрыто всё, кроме подсистемы отчётов —
её надо мерить отдельно, когда дойдут руки.
