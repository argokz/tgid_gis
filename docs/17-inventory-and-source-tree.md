# Общий инвентарь потребителей БД и структура исходников

## Инструмент

`tools/db_consumers.py` заменяет три прежних (`sety_tables.py`,
`gid8_tables.py`, `public_inventory.py`). Разница не только в объёме —
в направлении: вывод строится **от отношения БД к коду**, а не
наоборот. Вопрос всегда один — «кто это трогает», и ответ учитывает:

* SQL-обращения (`FROM`/`JOIN`/`INSERT`/`UPDATE`/`DELETE`) — с фильтром
  по контексту, чтобы «read from the table» в комментарии не считалось;
* упоминания словом — переменные, `.ui`, имя слоя в настройках;
* динамическую подстановку — не разбирается, но считается, чтобы вывод
  «никто не обращается» не оказался ложным;
* зависимости внутри самой БД — представления, внешние ключи, тела
  функций, каталог слоёв. Таблица без единого упоминания в коде может
  быть жива через них.

У каждого потребителя свой порядок поиска — это и есть источник
предыдущих трёх ошибок (шаги 58, 60): критерий «используется» смотрел
не всех, и таблицы уезжали на чердак, а потом возвращались.

```bash
python tools/db_consumers.py --db tgid_gis --json docs/schema/db_consumers.json
python tools/db_consumers.py --db tgid_gis --table nodes
```

## Находка: два дерева исходников gid8

`H:\projects\tgid-app-new\gid8` (вне git) и
`tgid_gis\gid8\gid8` (внутри репозитория, с шага 57) — **разные копии**,
`db.cpp` между ними отличается.

**Собирается вторая.** `tools/build_gid8.ps1` по умолчанию берёт
`..\gid8\gid8` относительно `tools` — это `tgid_gis\gid8\gid8`.

Копия в репозитории уже содержит более полное исправление
`search_path`, чем то, что было сделано в внешней копии в начале этой
сессии: включает `meta`, применено во всех точках подключения через
`configureTgidPostgreSqlSession()`, а не в одной. Внешняя копия
(`H:\projects\tgid-app-new\gid8`) не собирается и не должна править
С++ — правки туда молча теряются.

Движок расчёта устроен иначе: `sety` существует тоже в двух копиях
(`H:\projects\tgid-app-new\gid8\python\sety` и
`tgid_gis\gid8\python\sety`), но выполняется **внешняя** — все
инструменты (`bench_calc.py`, `ab_calc.py`, `recalc_all.ps1`) указывают
на неё явно. Копии пока идентичны (`net_mode.py` сверен), но синхронизация
ручная, и это тот же риск, что и с `db.cpp`: правка не туда — правка
в никуда.

**Практическое правило:** перед правкой C++ или Python-кода движка
проверять, что редактируемый файл — тот, что действительно
компилируется/выполняется, а не соседняя копия.

## Закрыт последний путь к `public` для gid8

`public.setpressnodes` была последней настоящей таблицей ТГИД,
используемой шестью потребителями сразу, и не имела представления в
`compat`. Класс `net.node_press_setting` существовал и был заполнен;
недостающим было только представление.

Перед переносом проверено, а не предположено:

* `node_id` в `net` совпадает с исходным `nodeid` для всех 5733 строк
  без исключений;
* представление простое (один `SELECT` из одной таблицы) — PostgreSQL
  делает его автообновляемым сам, `INSTEAD OF` не нужен;
* `UPDATE` и `INSERT` через представление доходят до
  `net.node_press_setting` — проверено
  [`sql/tests/test_compat_setpressnodes.sql`](../sql/tests/test_compat_setpressnodes.sql);
* единственная запись из самого приложения (`gidrSlot.cpp`) —
  `UPDATE fragment_resultID`; `INSERT` в исходниках gid8 не встречается,
  только в разовом скрипте миграции.

После [`sql/176_compat_setpressnodes.sql`](../sql/176_compat_setpressnodes.sql)
повторный инвентарь подтвердил: `gid8` и сборочная копия перестали
показывать `setpressnodes` как наследие. Оставшиеся упоминания
(`gid6`, `sety`, `potr5`) — не тот же дефект:

* у `sety` это исправный запасной путь для БД, ещё не переведённых на
  `net` (`is_net(conn) == False`);
* SQL-файлы в `gid6` выполняются через соединение самого gid8 и уже
  видят `compat` на практике — упрощённая модель порядка поиска в
  инструменте это не различает;
* `potr5` — отдельное, судя по всему нетронутое давно приложение вне
  текущего сопровождения, не проверялось.

## Что показал инвентарь дальше

* **Пустых таблиц-кандидатов на чердак — 0.** Прошлые находки (шаги 58,
  60) закрыты.
* **40 представлений без обращений в коде** — все `net.*_wgs84`. Это не
  потеря: они существуют для внешнего ГИС (QGIS, ArcGIS), который
  подключается к БД напрямую и в код проекта не входит.
* **1 имя используется несколькими потребителями и не разрешается нигде** —
  `magistrali`. Уже разобрано в шаге 52: дубль `ref.magistrals`,
  решение о выборе авторитетной версии — за заказчиком.
* Основной объём «не найдено» (673 записи) — шум разбора: системные
  каталоги (`pg_class`, `pg_attribute`), вызовы функций без скобок в
  многострочных объявлениях, короткие слова. Отфильтровано в JSON
  отдельно от значимых находок.
