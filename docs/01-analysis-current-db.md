Обследование выполнено на живой базе: PostgreSQL 16.6, порт 5440, БД `almatygid`, размер **637 MB**.
Исходные данные выгружены скриптом [`tools/dump_schema.py`](../tools/dump_schema.py) в

## 1.3 Как программа читает схему

Запросы чтения **не зашиты в код** — они лежат во внешних SQL-файлах и грузятся в рантайме:

- `sql3/us.sql` — узлы, [`cxema/read_nodes.cpp:225`](../../gid8/gid8/cxema/read_nodes.cpp)
- `sql3/ut.sql` — линии, [`cxema/read_lines.cpp:192`](../../gid8/gid8/cxema/read_lines.cpp)

Файл `sql3/us.sql` служит ещё и маркером установки — по нему `main.cpp` ищет рабочий каталог.

Обе выборки построены по одному шаблону: базовая таблица + `LEFT JOIN` на каждый подтип +
`CASE ... END AS type_txt`, возвращающий двухбуквенный код типа (`PR`, `PO`, `IS`, `HS`, `C3`, `US2`, `US`).

- `us.sql`: 6 LEFT JOIN подтипов + агрегирующий подзапрос по `CALCULATION` + 4 JOIN результатов расчёта.
- `ut.sql`: **14 LEFT JOIN подтипов** + подзапрос + **12 JOIN таблиц результатов** (`UT_OUT`, `NS_OUT`,
  `RS_OUT`, `BP_OUT`, `OK_OUT`, каждая дважды — для подачи и обратки).

Фильтр фрагмента дописывается **конкатенацией строк** к готовому тексту:

```cpp
q += QString(" AND n.fileID IN (%1)").arg(par);   // read_nodes.cpp:243
q += QString(" AND n1.fileID IN (%1)").arg(par);  // read_lines.cpp:212
```

Плейсхолдер `$user_gid$` подставляется через `QString::replace`. Параметризованных запросов нет.

## 1.5 Найденные дефекты данных и структуры

1. **Геометрия задублирована и рассогласована.** Программа читает `nodes.x/y` и текстовое поле
   `linesobj.coords` (формат `"x y,x y,"`, парсится `CCoordList::loadStr`). Колонки PostGIS `shape`
   заполнены частично и в расчёте не используются:

   | | всего (removed=0) | `shape` заполнен | `shape` пуст, но координаты есть | геометрии нет вовсе |
   |---|---|---|---|---|
   | `nodes` | 86 624 | 53 966 | 37 503 | 42 |
   | `linesobj` | 121 058 | 51 299 | 21 021 | 54 120 |

   То есть **для QGIS сейчас видно меньше половины сети**.

2. **Треть `linesobj` — не линии.** У 40 422 из 121 058 живых записей `nodeid1`/`nodeid2`
   равны NULL: это оборудование внутренних схем тепловых пунктов (шайбы, задвижки,
   элеваторы), у которого нет и не может быть координат. Подробный разбор —
   в [02-target-model.md](02-target-model.md), раздел «Открытие».
   Отдельно: `heatpipesections` содержит 1 981 строку из 98 019, ссылающуюся
   на несуществующий `linesobj.id` — вот это уже настоящие битые ссылки.

3. **Пары таблиц с одинаковым числом строк**: `obekty` / `tablitsa1` (по 38 247),
   `zhile` / `zhile1` (по 7 962), `organizations` / `organizatsii_vladeltsy` (по 16 579),
   `vvod_v_zdanie` / `vvody_v_zdanie` (по 5 463), `spisok_ulits` / `spisok_ulits_staryy`.

   Здесь я сначала написал «очевидные копии» — **это оказалось неверно**.
   Разбор с проверкой содержимого — [06-duplicate-tables.md](06-duplicate-tables.md):
   у `obekty` и `tablitsa1` совпадают структура и число строк, но данные различаются
   полностью; у `zhile` 25 колонок против 10 у `zhile1`. Решающий признак — ссылки
   из кода: на `tablitsa1` и `zhile1` их ноль.

4. **Механизм GIS-синхронизации заброшен.** Колонки `globalid`, `gistable`, `sync`, `gis`, `sync_tgid`
   есть в `nodes` и `linesobj`, но `gistable` пуст у всех 86 624 записей.

5. **Аудит съедает базу.** `audit_log` + `changed_object` = 125 MB из 637 MB (20 %),
   без партиционирования и без ретенции.

6. **Индексов почти нет.** На `nodes` — только PK, `fileid`, GiST по `shape`. На подтипах
   (`heatpipesections.lineid`, `realconsumers.nodeid`, …) индексов **нет**, хотя именно по ним идут все джойны.

7. **SRID 9998** — локальная СК. Для работы во внешних ГИС нужен корректный `spatial_ref_sys`
   с proj4-строкой и трансформация в 4326/3857.

## 1.6 Вывод

Текущая модель — «таблица-надтип + N таблиц-подтипов», склеиваемая мега-джойном на каждый показ схемы.
Для внешних ГИС она непригодна: QGIS не умеет открыть «объект», размазанный по `nodes` + `realconsumers`,
и не видит 60 % геометрии.

Целевая модель — **одна таблица на один тип объекта**, с собственной колонкой `geometry` как единственным
источником координат, реальными FK и индексами. Проект целевой схемы — в
[`docs/02-target-model.md`](02-target-model.md).
