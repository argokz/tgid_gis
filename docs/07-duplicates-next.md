# Дубли и спорные: что решать дальше

Краткая выжимка из [06-duplicate-tables.md](06-duplicate-tables.md),
[dubli_generalizedconsumers.sql](../sql/queries/dubli_generalizedconsumers.sql)
и [spornye_obekty.sql](../sql/queries/spornye_obekty.sql).

## Уже закрыто автоматически

| Тема | Решение в коде |
|---|---|
| Дубли строк в subtype на один `nodeid` | Выбор по `net.load_score` / `net.row_rank` (нагрузки ×1000), не по `max(id)` |
| Проигравшая строка | В `net.object_variant`, объект помечен `needs_review` |
| Узел в двух классах сразу | Объектом становится один класс; вторая строка — в `object_variant` + subtype view через `UNION ALL` |
| Справочники-«близнецы» (`tablitsa1`, `zhile1` …) | В `net` не переносятся; кандидаты на удаление после согласования |

## Решения заказчика (очередь)

1. **Три уникальных спорных потребителя** (не 23 и не 121 — копии фрагментов
   размножают одни и те же пары). Открыть секцию 2–3 в `spornye_obekty.sql`,
   сравнить нагрузки/высоту, вызвать:
   ```sql
   SELECT net.apply_variant(<src_id>, '<src_table>');  -- выбрать отвергнутую
   -- или оставить текущую и снять метку вручную / отдельной командой
   ```
2. **Фрагменты-копии** (узлы с `fileid` 76/78/80/82… и 91/93/95/97): в таблице
   `fragments` многих из этих id **нет** (например 80, 91) — sety сразу падает
   с «Какая-то ошибка!!!!». Решить: завести строки в `fragments` или не считать
   эти fileid рабочими схемами.
3. **Чистка справочников** после выгрузки: `tablitsa1`, `zhile1`; проверить
   ссылки на `spisok_ulits_staryy`.

## Не делать молча

- Не удалять «лишнюю» строку subtype без записи в `object_variant`.
- Не считать `externalcodeid` ключом одного физического объекта — у копий
  фрагментов он разный при одинаковых координатах и имени.
