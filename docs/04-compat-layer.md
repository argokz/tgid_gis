# Шаг 9. Слой совместимости

Цель — дать приложению работать со схемой `net`, не меняя его код.

## 9.1 Что сделано

`net.v_nodes` и `net.v_linesobj` — представления, повторяющие форму прежних
`public.nodes` (44 колонки) и `public.linesobj` (26 колонок), но читающие из объектных
таблиц `net`. Колонки, которых в новой модели нет, восстанавливаются:

| Колонка | Откуда берётся |
|---|---|
| `x`, `y` | из геометрии: `ST_X(geom) * 100`, `-ST_Y(geom) * 100` |
| `shape` | это и есть `geom` |
| `coords` | вычисляемая колонка `coords_legacy` |
| `removed` | `CASE WHEN removed_at IS NULL THEN 0 ELSE 1 END` |
| `fileid` (линии) | сохранённый `fileid_src`, а не фрагмент узла |

Представления создаются **рядом** с оригиналом, ничего не переименовывая, — это позволяет
сверить их с `public` до какого-либо переключения.

## 9.2 Идентификаторы сохранены

Изначально объекты в `net` получали новые `id` из общей последовательности. Проверка
показала, что так делать нельзя: **139 колонок схемы `public`** (`nodeid`, `lineid`,
`nodeid1`, `nodeid2`) ссылаются на объекты по идентификатору, и перенумерация порвала бы
все эти связи.

Теперь `id` переносится из `public` как есть. Реестры узлов и линий раздельные, поэтому
совпадение `id` узла и `id` линии допустимо. Последовательность сдвинута на 604332 —
выше всех занятых значений.

## 9.3 Результат сверки

[`tools/check_compat.py`](../tools/check_compat.py) сравнивает **каждую колонку каждой
перенесённой строки**: 91 490 узлов и 86 016 линий.

**Неожиданных расхождений: 0.**

Ожидаемые расхождения и их причины:

| Колонка | Строк | Причина |
|---|---|---|
| `sync_tgid`, `sync`, `gis`, `gistable`, `globalid` | до 66 050 | заброшенный механизм GIS-синхронизации, не переносится |
| `shape` | 38 474 / 36 187 | в `public` заполнен частично и устарел, в `net` построен заново |
| `coords` | 28 882 | в `net` вычисляется из геометрии, отличается форматирование числа |
| `idremoved` | 4 893 / 5 388 | механизм удаления заменён на `removed_at` |
| `id_old` | ~2 000 | служебное поле прежней миграции |

Расхождение по `coords` проверено **по смыслу, а не по тексту**: из 28 882 строк
с другим текстом набор точек совпал у 28 847. У оставшихся 35 максимальное расхождение
самих точек — **0.67 микрометра**: это разрядность `double`, а не ошибка переноса.

Две ошибки были найдены именно этой сверкой и исправлены:

- `removed` — в представлении стояла константа `0`, хотя 4 908 узлов и 5 402 линии
  помечены удалёнными;
- `fileid` линии — подставлялся фрагмент начального узла, тогда как собственный
  `linesobj.fileid` заполнен лишь у 22 212 из 80 646 строк. Теперь сохраняется исходное
  значение.

## 9.4 Переключение и откат — проверены на живой базе

```bash
psql -f sql/040_switch_to_net.sql        # nodes -> nodes_legacy, вместо неё представление
psql -f sql/041_rollback_to_public.sql   # обратно
```

Переключение сводится к переименованию: данные не копируются и не удаляются.
Оба скрипта транзакционные, в `040` встроена страховка — отказ, если схема `net` пуста.

Проверено фактическим прогоном: после переключения `public.nodes` и `public.linesobj`
становятся представлениями, после отката — снова таблицами с исходным числом строк
(91 532 и 126 460).

### Важное наблюдение

После переключения **старый, никак не изменённый `us.sql` продолжает работать** — но
становится медленнее: 479 мс против 254 мс на исходных таблицах. Union-представление
не бесплатно.

Смысл в том, что переключение схемы и замена файлов запросов — **два разных шага, и нужны
оба**. На одном фрагменте:

| | старый `us.sql` | новый `us_net.sql` |
|---|---|---|
| до переключения | 254 мс | — |
| после переключения | 479 мс | **106 мс** |

Совместимость даёт возможность не сломаться сразу, а не выигрыш сама по себе.

## 9.5 Ограничение: запись пока не поддержана

После переключения `public.nodes` и `public.linesobj` доступны **только для чтения**.
Для режима просмотра, расчёта и выгрузки в ГИС этого достаточно; для редактирования — нет.

Причина не техническая, а модельная. В прежней схеме объект создавался в два приёма:
сначала строка в `nodes`, потом строка в таблице-подтипе, которая и задавала тип.
В новой модели **тип объекта — это имя таблицы**, поэтому в момент вставки в `public.nodes`
ещё неизвестно, куда класть строку.

Варианты:

1. `INSTEAD OF`-триггеры, которые кладут новый объект в `net.node_plain`, а при появлении
   строки в подтипе переносят его в нужную таблицу. Работает без правки приложения,
   но перенос строки между таблицами на каждое создание объекта — медленно и хрупко.
2. Изменить путь записи в самом приложении: создавать объект сразу в нужной таблице.
   Правильнее и быстрее, но требует правки C++ и пересборки.

Рекомендую второй вариант. Точки правки в коде:

| Файл | Что делает |
|---|---|
| [`gidview/b5.cpp`](../../gid8/gid8/gidview/b5.cpp) | `addNodeUS`, `addLine` — создание объектов |
| [`cxema/cxema_edit.cpp`](../../gid8/gid8/cxema/cxema_edit.cpp) | правка схемы |
| [`gidview/gidr_add.cpp`](../../gid8/gid8/gidview/gidr_add.cpp) | добавление объектов из интерфейса |
| [`gidview/gidr_del.cpp`](../../gid8/gid8/gidview/gidr_del.cpp) | удаление: `removed = 1` заменить на `removed_at = now()` |
| [`cxema/undo_gid.cpp`](../../gid8/gid8/cxema/undo_gid.cpp) | отмена операций |

Отдельная задача — заменить конкатенацию строк на параметризованные запросы
(`read_nodes.cpp:243`, `read_lines.cpp:212` и ещё 278 мест с `query_exec`).

## 9.6 Текущее состояние базы

БД `almatygid` оставлена **в исходном состоянии**: `public.nodes` и `public.linesobj` —
обычные таблицы, приложение работает как раньше. Схема `net` наполнена и проверена,
переключение выполняется одной командой, когда потребуется.
